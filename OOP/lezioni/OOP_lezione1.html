1. Stile e Convenzioni: Scrivere Codice Leggibile

Prima di addentrarci nei concetti complessi, è fondamentale stabilire delle regole di base per scrivere codice che non sia solo funzionante, ma anche leggibile, manutenibile e professionale. Un buon software si riconosce prima di tutto da come è scritto.

Nomi Significativi (Intention-Revealing Names)

La scelta dei nomi per variabili, metodi e classi è una delle decisioni più importanti che un programmatore prende. Un nome deve rivelare l'intenzione e il ruolo dell'elemento che identifica.

💡 Buona Pratica
Evita nomi generici, abbreviati o che possano creare disinformazione. 

// --- MALE (Cattiva Pratica) ---
int d; // "d" cosa rappresenta? Giorni? Distanza? Dati?
List a1; // "a1" non dà alcun contesto.

String genymdhms; // Difficile da pronunciare e da ricordare.
String phoneString; // Il suffisso "String" è ridondante.

// --- BENE (Buona Pratica) ---
int elapsedTimeInDays;
List sourceAccounts;

String generationTimestamp;
String phoneNumber;

Convenzioni Standard di Java

Seguire le convenzioni standard del linguaggio rende il codice immediatamente familiare a qualsiasi altro sviluppatore Java.

  • Classi e Interfacce: Usano `PascalCase` (o `UpperCamelCase`). Es: `Student`, `ShapeFactory`, `List`.
  • Metodi e Variabili: Usano `camelCase` (o `lowerCamelCase`). Es: `calculateArea`, `studentName`.
  • Costanti: Usano `UPPER_CASE_WITH_UNDERSCORES`. Es: `MAX_CONNECTIONS`, `DEFAULT_PORT`.
  • Package: Usano `lowercase.with.dots`. Es: `it.uniud.poo.utils`.

2. Tipi di Dati: Primitivi vs Riferimento

Java distingue due categorie principali di tipi di dati, il cui comportamento in memoria è radicalmente diverso.

Tipi Primitivi

Sono i mattoni fondamentali del linguaggio. Rappresentano valori semplici e diretti. Ce ne sono otto: `boolean`, `char`, `byte`, `short`, `int`, `long`, `float`, `double`.

Tipi Riferimento (Oggetti)

Qualsiasi tipo che non sia primitivo è un tipo riferimento. Questo include classi che creiamo noi (`Student`), classi della libreria standard (come `String`, `ArrayList`) e array. Una variabile di tipo riferimento non contiene l'oggetto stesso, ma un **riferimento** (un puntatore o indirizzo di memoria) alla locazione in cui l'oggetto risiede.

Wrapper Classes, Boxing e Unboxing

Per ogni tipo primitivo, Java fornisce una classe "wrapper" corrispondente (es. `int` -> `Integer`, `char` -> `Character`). Queste classi permettono di trattare i valori primitivi come oggetti, ad esempio per inserirli in collezioni generiche come `List`.

Il processo di conversione da primitivo a wrapper è chiamato boxing, mentre il processo inverso è l'unboxing. Java gestisce queste conversioni automaticamente (autoboxing).

⚠️ Attenzione alla Performance
L'autoboxing, sebbene comodo, può avere un impatto negativo sulle prestazioni se avviene all'interno di un ciclo molto lungo, poiché ad ogni iterazione viene creato un nuovo oggetto. 

// Esempio di autoboxing inefficiente
Long sum = 0L; // sum è un oggetto Long
// In questo ciclo, ad ogni iterazione, viene creato un nuovo oggetto Long
// per contenere il risultato di 'sum + i', e 'sum' viene aggiornato per puntare a questo nuovo oggetto.
for (long i = 0; i <= 1_000_000; i++) {
    sum += i; // Inefficace: sum = Long.valueOf(sum.longValue() + i);
}

// Esempio efficiente con tipo primitivo
long sumPrimitive = 0L; // sumPrimitive è un valore primitivo
for (long i = 0; i <= 1_000_000; i++) {
    sumPrimitive += i; // Molto più veloce: nessuna creazione di oggetti.
}

3. Allocazione in Memoria: Stack e Heap

Comprendere dove risiedono i dati è fondamentale per capire il comportamento del programma, specialmente per quanto riguarda la mutabilità e il passaggio di parametri.

  • Stack (Pila): È una zona di memoria gestita con logica LIFO (Last-In, First-Out). Contiene i **tipi primitivi** e i **riferimenti agli oggetti**. Ogni chiamata a metodo crea un nuovo "frame" sullo stack per le sue variabili locali. Quando il metodo termina, il suo frame viene rimosso.
  • Heap: È una grande area di memoria dove vengono allocati dinamicamente tutti gli **oggetti** (creati con `new`). La gestione dello spazio nell'heap è compito del **Garbage Collector**, che dealloca automaticamente gli oggetti che non sono più raggiungibili (cioè, non ci sono più riferimenti attivi che puntano a loro).

4. Mutabilità e Uguaglianza

Questi due concetti sono strettamente collegati e sono una fonte comune di bug se non compresi a fondo.

Oggetti Mutabili vs. Immutabili

  • Un oggetto è mutabile se il suo stato interno può essere modificato dopo la sua creazione. Esempi: `ArrayList`, `StringBuilder`, la maggior parte delle classi di dominio personalizzate.
  • Un oggetto è immutabile se il suo stato non può mai essere cambiato dopo la creazione. Ogni "modifica" in realtà crea un nuovo oggetto. Esempio per eccellenza: `String`.

// Esempio di immutabilità di String
String s1 = "Ciao";
String s2 = s1; // s2 ora punta allo stesso oggetto "Ciao" di s1
s1 = s1 + " Mondo"; // VIENE CREATO UN NUOVO OGGETTO "Ciao Mondo". s1 ora punta a questo nuovo oggetto.

System.out.println(s2); // Stampa "Ciao", perché s2 punta ancora all'oggetto originale.

Identità (`==`) vs. Uguaglianza (`.equals()`)

Questa è una delle distinzioni più importanti in Java.

  • Identità (`==`): Controlla se due variabili di riferimento puntano **allo stesso identico oggetto in memoria**. Per i tipi primitivi, controlla se i valori sono uguali.
  • Uguaglianza (`.equals()`): È un metodo che, per convenzione, dovrebbe controllare se due oggetti sono "logicamente" equivalenti, cioè se hanno lo stesso stato significativo. La classe `Object` fornisce un'implementazione di default che si comporta come `==`. Per ottenere un confronto basato sul contenuto, **è necessario fare l'override del metodo `.equals()`** (e, di conseguenza, anche di `.hashCode()`).

String literal1 = "Java";
String literal2 = "Java";
String obj1 = new String("Java");

System.out.println(literal1 == literal2); // true (il compilatore riusa lo stesso oggetto per le stringhe letterali)
System.out.println(literal1 == obj1);    // false (obj1 è un nuovo oggetto, anche se con lo stesso contenuto)
System.out.println(literal1.equals(obj1)); // true (il contenuto è lo stesso, il metodo equals di String controlla i caratteri)

StringBuilder sb1 = new StringBuilder("Test");
StringBuilder sb2 = new StringBuilder("Test");

System.out.println(sb1 == sb2);         // false (due oggetti distinti)
System.out.println(sb1.equals(sb2));    // false! (StringBuilder non fa l'override di equals, quindi usa il comportamento di Object, che è come ==)
⚠️ Il Contratto tra equals() e hashCode()

Quando si fa l'override del metodo .equals(), è obbligatorio fare l'override anche di .hashCode(). Il contratto ufficiale di Java richiede che:

  • Se due oggetti sono uguali secondo .equals(), allora devono avere lo stesso valore di hashCode().
  • Se due oggetti hanno lo stesso hashCode(), non è detto che siano uguali secondo .equals() (collisione hash).

Violare questo contratto porta a comportamenti imprevedibili e a bug quando si usano gli oggetti in collezioni basate su hash come HashSet e HashMap.

5. Classi, Oggetti e Visibilità

Una classe è un "modello" o "progetto" per creare oggetti. Un oggetto è un'istanza di una classe.

Variabili di Istanza e Variabili di Classe

  • Variabile di Istanza: Ogni oggetto ha la sua copia personale. Se `studente1.nome = "Mario"` e `studente2.nome = "Luigi"`, ogni oggetto ha il suo valore.
  • Variabile di Classe (`static`): Esiste una sola copia di questa variabile, condivisa da **tutte le istanze** della classe. È associata alla classe stessa, non ai singoli oggetti. È utile per contatori o costanti.

Modificatori di Visibilità

La visibilità controlla chi può accedere a classi, metodi e variabili. È uno strumento fondamentale per l'**incapsulamento**.

  1. `private`: Accessibile solo dall'interno della stessa classe. **È la scelta di default per tutte le variabili di istanza per proteggere lo stato interno di un oggetto.**
  2. Package-private (nessun modificatore): Accessibile solo da classi nello stesso package.
  3. `protected`: Accessibile da classi nello stesso package E da sottoclassi (anche se in package diversi).
  4. `public`: Accessibile da qualsiasi classe, ovunque. Va usato con parsimonia per l'API pubblica di una classe.

6. Metodi: Overloading e Dispatching

Overloading

L'overloading (o sovraccarico) consiste nel definire più metodi con lo **stesso nome** ma con una **lista di parametri diversa** (per numero o per tipo) all'interno della stessa classe. Il compilatore decide quale versione chiamare in base ai tipi *apparenti* degli argomenti passati.

Se esistono più conversioni possibili, il compilatore sceglie la versione "più specifica", cioè quella che richiede il minor numero di conversioni da tipo più specifico a tipo più generico (es. da `int` a `long` è preferibile che da `int` a `double`). Se la scelta è ambigua, si ottiene un errore di compilazione.

Method Dispatching (Polimorfismo)

Il dispatching è il processo con cui la JVM decide quale implementazione di un metodo eseguire. È alla base del polimorfismo.

La decisione si basa su due fattori:

  1. Il tipo apparente degli argomenti (Compile-time): Determina quale metodo *overload* viene selezionato.
  2. Il tipo reale dell'oggetto su cui il metodo è chiamato (Run-time): Determina quale versione *overridden* (sovrascritta) del metodo viene eseguita.
💡 Programmare verso le Interfacce
Una delle pratiche più importanti dell'OOP è "programmare verso un'interfaccia, non verso un'implementazione". Questo significa dichiarare le variabili con il tipo più generale possibile (es. `List` invece di `ArrayList`), sfruttando il polimorfismo per nascondere i dettagli implementativi e rendere il codice più flessibile. 

// Buona pratica: dichiaro la variabile con il tipo interfaccia
List names = new ArrayList<>(); 

// Il mio metodo accetta qualsiasi implementazione di List
public void processNames(List nameList) {
    // ... logica che usa solo i metodi di List
}

// Posso passare un ArrayList...
processNames(names);
// ... o potrei passare un LinkedList senza cambiare il metodo processNames!
List otherNames = new LinkedList<>();
processNames(otherNames);
