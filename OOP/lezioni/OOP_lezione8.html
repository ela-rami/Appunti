1. Cosa sono i Design Pattern Creazionali?

I Design Pattern Creazionali sono soluzioni collaudate a problemi ricorrenti legati al processo di creazione degli oggetti. Il loro obiettivo principale è aumentare la flessibilità e il riutilizzo del codice, nascondendo la logica di istanziazione e disaccoppiando il codice client dalle classi concrete che deve utilizzare.

💡 Il Problema Comune
L'uso diretto dell'operatore `new` (es. `Veicolo v = new Automobile();`) crea un accoppiamento forte tra il codice client e la classe concreta (`Automobile`). Se in futuro vogliamo creare un `Camion` invece di un'`Automobile`, dobbiamo modificare il codice client. I pattern creazionali risolvono questo problema.

In questa lezione analizzeremo tre dei pattern creazionali più importanti: Factory Method, Abstract Factory e Builder.

2. Factory Method Pattern

Il Factory Method è un pattern che definisce un'interfaccia (un metodo) per creare un oggetto, ma lascia alle sottoclassi la decisione di quale classe concreta istanziare. In pratica, delega la logica di istanziazione a una classe specializzata, la "fabbrica".

Struttura

                        classDiagram
                            direction LR
                            class Client
                            class ShapeFactory {
                                +getShape(shapeType: String): Shape
                            }
                            class Shape {
                                <>
                                +draw()
                            }
                            class Circle {
                                +draw()
                            }
                            class Square {
                                +draw()
                            }

                            ShapeFactory ..> Shape : creates

                            Square --|> Shape
  • Product (Shape): L'interfaccia o la classe astratta degli oggetti che la factory crea.
  • ConcreteProduct (Circle, Square): Le implementazioni concrete dell'interfaccia Product.
  • Creator (ShapeFactory): La classe che contiene il "factory method" (`getShape`). Questo metodo restituisce un oggetto di tipo `Product`.
  • Client: Utilizza la `ShapeFactory` per ottenere un oggetto `Shape`, senza sapere (o preoccuparsi) se sta ottenendo un `Circle` o uno `Square`.

2.1. Esempio: Fabbrica di Forme

Vediamo come implementare una factory per creare diverse forme geometriche.


// 1. L'interfaccia Product
public interface Shape {
    void draw();
}

// 2. I ConcreteProduct
public class Circle implements Shape {
    @Override
    public void draw() { System.out.println("Disegno un cerchio."); }
}
public class Square implements Shape {
    @Override
    public void draw() { System.out.println("Disegno un quadrato."); }
}

// 3. La classe Creator (la Factory)
public class ShapeFactory {
    // Il factory method
    public Shape getShape(String shapeType) {
        if (shapeType == null) {
            return null;
        }
        if (shapeType.equalsIgnoreCase("CIRCLE")) {
            return new Circle();
        } else if (shapeType.equalsIgnoreCase("SQUARE")) {
            return new Square();
        }
        return null; // O lancia un'eccezione
    }
}

// 4. Il Client
public class Main {
    public static void main(String[] args) {
        ShapeFactory shapeFactory = new ShapeFactory();

        // Il client non usa 'new Circle()', ma chiede alla factory.
        Shape shape1 = shapeFactory.getShape("CIRCLE");
        shape1.draw(); // Disaccoppiato!

        Shape shape2 = shapeFactory.getShape("SQUARE");
        shape2.draw();
    }
}
💡 Vantaggi
Il client è completamente disaccoppiato dalle classi concrete `Circle` e `Square`. Se domani aggiungiamo una nuova forma `Triangle`, il client non dovrà essere modificato. Dovremo solo aggiornare la logica interna della `ShapeFactory`.

3. Abstract Factory Pattern

L'Abstract Factory è un "super-pattern" che si occupa di creare famiglie di oggetti correlati o dipendenti senza specificare le loro classi concrete. È come avere una "fabbrica di fabbriche".

Si usa quando il sistema deve essere indipendente da come i suoi prodotti vengono creati, composti e rappresentati, e quando si deve configurare il sistema con una di più famiglie di prodotti.

3.1. Esempio: Fabbrica di UI Kit

Immaginiamo di dover creare un'interfaccia utente che può avere temi diversi (es. Windows, macOS). Ogni tema ha la sua famiglia di componenti (bottoni, checkbox) correlati.


// 1. Interfacce per i prodotti astratti
interface Button { void paint(); }
interface Checkbox { void paint(); }

// 2. Implementazioni concrete per la famiglia "Windows"
class WinButton implements Button {
    public void paint() { System.out.println("Rendering di un bottone stile Windows."); }
}
class WinCheckbox implements Checkbox {
    public void paint() { System.out.println("Rendering di una checkbox stile Windows."); }
}

// 3. Implementazioni concrete per la famiglia "macOS"
class MacButton implements Button {
    public void paint() { System.out.println("Rendering di un bottone stile macOS."); }
}
class MacCheckbox implements Checkbox {
    public void paint() { System.out.println("Rendering di una checkbox stile macOS."); }
}

// 4. L'interfaccia Abstract Factory
interface GUIFactory {
    Button createButton();
    Checkbox createCheckbox();
}

// 5. Le fabbriche concrete per ogni famiglia
class WinFactory implements GUIFactory {
    public Button createButton() { return new WinButton(); }
    public Checkbox createCheckbox() { return new WinCheckbox(); }
}
class MacFactory implements GUIFactory {
    public Button createButton() { return new MacButton(); }
    public Checkbox createCheckbox() { return new MacCheckbox(); }
}

// 6. Il Client
public class Application {
    private Button button;
    private Checkbox checkbox;

    public Application(GUIFactory factory) {
        // Il client usa la factory astratta per creare i componenti,
        // senza sapere quali sono le classi concrete.
        button = factory.createButton();
        checkbox = factory.createCheckbox();
    }
    public void paint() {
        button.paint();
        checkbox.paint();
    }

    public static void main(String[] args) {
        String osName = System.getProperty("os.name").toLowerCase();
        GUIFactory factory;
        if (osName.contains("mac")) {
            factory = new MacFactory();
        } else {
            factory = new WinFactory();
        }
        Application app = new Application(factory);
        app.paint();
    }
}

4. Builder Pattern

Il Builder è un pattern creazionale che permette di costruire un oggetto complesso passo dopo passo. Il pattern separa il processo di costruzione di un oggetto dalla sua rappresentazione finale, permettendo allo stesso processo di costruzione di creare rappresentazioni diverse.

È particolarmente utile quando un oggetto ha molti parametri nel costruttore, alcuni obbligatori e altri opzionali, per evitare costruttori con liste di parametri infinite (i "telescoping constructors").

Struttura

Il pattern usa una classe interna statica (`Builder`) per raccogliere i parametri di costruzione. Spesso utilizza uno stile di programmazione "fluente" (fluent interface), in cui i metodi di impostazione restituiscono l'istanza del builder stesso per permettere la concatenazione delle chiamate.

4.1. Esempio: Costruzione di un Computer

Immaginiamo di dover costruire un oggetto `Computer` con molti componenti, alcuni obbligatori (RAM, HDD) e altri opzionali (scheda grafica, bluetooth).


// Il Prodotto da costruire
public class Computer {
    // Obbligatori
    private String HDD;
    private String RAM;
    // Opzionali
    private boolean isGraphicsCardEnabled;
    private boolean isBluetoothEnabled;

    // Il costruttore è privato! L'unico modo per creare un Computer è tramite il suo Builder.
    private Computer(ComputerBuilder builder) {
        this.HDD = builder.HDD;
        this.RAM = builder.RAM;
        this.isGraphicsCardEnabled = builder.isGraphicsCardEnabled;
        this.isBluetoothEnabled = builder.isBluetoothEnabled;
    }
    
    // ... metodi getter ...
    @Override
    public String toString() { /* ... */ }

    // La classe Builder interna e statica
    public static class ComputerBuilder {
        // Ha gli stessi campi del prodotto
        private String HDD;
        private String RAM;
        private boolean isGraphicsCardEnabled;
        private boolean isBluetoothEnabled;

        // Il costruttore del Builder prende solo i parametri obbligatori
        public ComputerBuilder(String hdd, String ram) {
            this.HDD = hdd;
            this.RAM = ram;
        }

        // Metodi per i parametri opzionali. Restituiscono `this` per la concatenazione.
        public ComputerBuilder setGraphicsCardEnabled(boolean isGraphicsCardEnabled) {
            this.isGraphicsCardEnabled = isGraphicsCardEnabled;
            return this;
        }

        public ComputerBuilder setBluetoothEnabled(boolean isBluetoothEnabled) {
            this.isBluetoothEnabled = isBluetoothEnabled;
            return this;
        }
        
        // Il metodo build() crea l'oggetto Computer finale.
        public Computer build() {
            return new Computer(this);
        }
    }
}

// Il Client
public class Main {
    public static void main(String[] args) {
        // Uso del Builder con interfaccia fluente
        Computer pc = new Computer.ComputerBuilder("500 GB", "8 GB")
                            .setBluetoothEnabled(true)
                            .setGraphicsCardEnabled(true)
                            .build();

        System.out.println("Computer Config: " + pc);
    }
}
💡 Vantaggi del Builder
  • Leggibilità: Il codice client è molto più leggibile rispetto a un costruttore con molti parametri booleani o `null`.
  • Flessibilità: Permette di creare oggetti complessi passo dopo passo e di avere molteplici configurazioni.
  • Immutabilità: Il pattern Builder si sposa benissimo con la creazione di oggetti immutabili, poiché lo stato viene fissato una sola volta nel metodo `build()`.
