1. Responsibility-Driven Design (RDD)

La progettazione orientata agli oggetti (OOP) non riguarda solo la scrittura di classi, ma la creazione di un sistema di oggetti che collaborano. L'approccio RDD si concentra sul definire prima le responsabilità del sistema e poi assegnarle agli oggetti più appropriati.

  • Responsabilità: Un contratto o un obbligo di un componente. Descrive il comportamento di alto livello che un oggetto deve garantire.
  • Collaborazione: Un oggetto adempie alle sue responsabilità o da solo o collaborando con altri oggetti, delegando parte del lavoro.
💡 La Domanda Chiave del Design
La domanda fondamentale da porsi durante la progettazione non è "che stato ha questo oggetto?", ma "cosa sa fare questo oggetto?" e "con chi deve parlare per farlo?". Il design guidato dalle responsabilità si focalizza prima sul comportamento e poi sullo stato.

2. Single Responsibility Principle (SRP)

Il Single Responsibility Principle (SRP) è il primo e forse il più importante dei principi SOLID, formalizzato da Robert C. Martin.

💡 Definizione di SRP
"Una classe dovrebbe avere una e una sola ragione per cambiare."

Questo non significa che una classe debba avere un solo metodo. Significa che tutti i metodi e le proprietà di una classe dovrebbero essere coesi e allineati attorno a una singola responsabilità o concetto di business.

Se una classe ha più di una responsabilità, queste responsabilità diventano accoppiate. Un cambiamento richiesto per una responsabilità potrebbe influenzare o rompere la logica dell'altra, rendendo il codice fragile e difficile da mantenere.

Esempio Pratico: La Classe `Fattura`

⚠️ Violazione dell'SRP

// Questa classe viola l'SRP perché ha DUE responsabilità.
public class Fattura {
    private List items;
    private double totale;

    // --- Responsabilità 1: Calcoli di Business ---
    public void aggiungiItem(Item item) { /* ... */ }
    public void calcolaTotale() { /* ... */ }
    
    // --- Responsabilità 2: Persistenza e Formattazione ---
    public void salvaSuDatabase() { /* Logica SQL per salvare la fattura */ }
    public String generaPDF() { /* Logica per creare un file PDF */ }
}

Problema: Se cambia il modo in cui calcoliamo il totale (es. aggiungendo l'IVA), dobbiamo modificare la classe. Se cambia il database (es. da MySQL a PostgreSQL) o la libreria PDF, dobbiamo modificare la stessa classe. Le due responsabilità sono accoppiate.

💡 Soluzione con SRP

La soluzione è separare le responsabilità in classi distinte:


// 1. Classe Fattura: solo logica di business
public class Fattura {
    private List items;
    private double totale;

    public void aggiungiItem(Item item) { /* ... */ }
    public void calcolaTotale() { /* ... */ }
}

// 2. Classe Repository: solo persistenza
public class FatturaRepository {
    public void salva(Fattura fattura) { /* Logica SQL */ }
}

// 3. Classe Service/Formatter: solo formattazione
public class FatturaPdfExporter {
    public byte[] esporta(Fattura fattura) { /* Logica per creare PDF */ }
}

Ora, ogni classe ha una sola ragione per cambiare. Il sistema è più modulare, testabile e manutenibile.

3. Dependency Inversion Principle (DIP)

Il Dependency Inversion Principle è un altro principio SOLID fondamentale per creare software disaccoppiato e flessibile.

💡 Definizione di DIP
  1. I moduli di alto livello non dovrebbero dipendere dai moduli di basso livello. Entrambi dovrebbero dipendere da astrazioni.
  2. Le astrazioni non dovrebbero dipendere dai dettagli. I dettagli dovrebbero dipendere dalle astrazioni.

In pratica, questo significa che il codice che contiene la logica di business importante (alto livello) non dovrebbe dipendere direttamente da classi concrete che gestiscono dettagli tecnici come database, file system o chiamate di rete (basso livello). Invece, entrambi dovrebbero dipendere da **interfacce** (astrazioni).

Esempio Pratico: Servizio di Notifica

⚠️ Violazione del DIP

// Modulo di basso livello (dettaglio)
public class EmailSender {
    public void inviaEmail(String destinatario, String messaggio) { /* ... */ }
}

// Modulo di alto livello (logica di business)
public class GestoreOrdini {
    private EmailSender emailSender; // Dipendenza DIRETTA da una classe concreta!

    public GestoreOrdini() {
        this.emailSender = new EmailSender(); // Accoppiamento forte!
    }

    public void processaOrdine(Ordine ordine) {
        // ... logica per processare l'ordine ...
        emailSender.inviaEmail(ordine.getClienteEmail(), "Il tuo ordine è stato spedito!");
    }
}

Problema: Il `GestoreOrdini` è saldamente accoppiato a `EmailSender`. Se domani volessimo inviare notifiche tramite SMS invece che email, dovremmo modificare la classe `GestoreOrdini`. Il modulo di alto livello dipende da un dettaglio di basso livello.

💡 Soluzione con DIP (Dependency Injection)

La soluzione è introdurre un'astrazione (un'interfaccia) e usare la Dependency Injection per "iniettare" l'implementazione concreta dall'esterno.


// 1. L'astrazione
public interface ServizioNotifica {
    void inviaNotifica(String destinatario, String messaggio);
}

// 2. Le implementazioni di basso livello dipendono dall'astrazione
public class EmailNotifier implements ServizioNotifica {
    @Override
    public void inviaNotifica(String destinatario, String messaggio) { /* invia email */ }
}

public class SmsNotifier implements ServizioNotifica {
    @Override
    public void inviaNotifica(String destinatario, String messaggio) { /* invia SMS */ }
}

// 3. Il modulo di alto livello dipende dall'astrazione
public class GestoreOrdini {
    // Dipende dall'INTERFACCIA, non dalla classe concreta
    private final ServizioNotifica servizioNotifica; 

    // L'implementazione concreta viene "iniettata" dall'esterno (es. nel costruttore)
    public GestoreOrdini(ServizioNotifica servizioNotifica) {
        this.servizioNotifica = servizioNotifica;
    }

    public void processaOrdine(Ordine ordine) {
        // ... logica ...
        servizioNotifica.inviaNotifica(ordine.getClienteEmail(), "Il tuo ordine è stato spedito!");
    }
}

// Nel Main o in una Factory, si configura il sistema:
// GestoreOrdini gestore = new GestoreOrdini(new EmailNotifier()); // Usa le email
// GestoreOrdini gestore = new GestoreOrdini(new SmsNotifier());   // Oppure usa gli SMS

4. Gli altri principi SOLID

SRP e DIP sono due dei cinque principi SOLID. Gli altri tre sono strettamente legati a quanto visto finora:

  • O - Open/Closed Principle (OCP): Un'entità software dovrebbe essere aperta all'estensione, ma chiusa alla modifica. Il DIP è una delle tecniche principali per ottenere l'OCP. Il nostro `GestoreOrdini` è chiuso alla modifica ma aperto all'estensione (possiamo aggiungere un `WhatsAppNotifier` senza toccare `GestoreOrdini`).
  • L - Liskov Substitution Principle (LSP): I sottotipi devono essere sostituibili ai loro supertipi. Lo abbiamo visto in dettaglio nella lezione precedente. È fondamentale perché il DIP funzioni correttamente.
  • I - Interface Segregation Principle (ISP): I client non dovrebbero essere forzati a dipendere da interfacce che non usano. È meglio avere molte interfacce piccole e specifiche piuttosto che una grande e generica.

5. Metodologia CRC (Class-Responsibility-Collaboration)

La metodologia CRC è una tecnica di brainstorming semplice e potente per il design orientato agli oggetti. Si basa sull'uso di semplici schede (originariamente, schede di cartone) per rappresentare ogni classe del sistema.

Ogni scheda è divisa in tre sezioni:

Nome della Classe

Responsabilità

  • Conosce/fa qualcosa.
  • Mantiene uno stato.
  • ...

Collaboratori

  • AltraClasse
  • ServizioEsterno

Come si usa?

  1. Identifica le Classi: Dal testo dei requisiti, estrai i "sostantivi" che potrebbero diventare classi (`Fattura`, `Cliente`, `Prodotto`).
  2. Assegna le Responsabilità: Per ogni classe, elenca le sue responsabilità principali (i "verbi" associati, es. `Fattura` -> "calcola totale").
  3. Identifica i Collaboratori: Se una classe ha bisogno di aiuto per adempiere a una responsabilità, elenca le altre classi (o interfacce) con cui deve collaborare.
  4. Simula Scenari: "Esegui" uno scenario d'uso muovendo fisicamente le schede e seguendo le interazioni. Questo aiuta a scoprire responsabilità mancanti o assegnate male.

La tecnica CRC è un ottimo modo per applicare il Responsibility-Driven Design e i principi SOLID in modo pratico e collaborativo, prima ancora di scrivere una sola riga di codice.
