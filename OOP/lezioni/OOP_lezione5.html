1. Famiglie di Tipi e Gerarchie

Nei problemi reali, spesso abbiamo a che fare con concetti che sono simili ma non identici. Ad esempio, `Automobile`, `Camion`, e `Moto` sono tutti tipi di `Veicolo`. Condividono proprietà comuni (es. una velocità, un proprietario) e comportamenti comuni (es. accelerare, frenare), ma hanno anche caratteristiche specifiche che li distinguono.

La Programmazione Orientata agli Oggetti ci fornisce gli strumenti per modellare queste relazioni attraverso le gerarchie di tipi. Una gerarchia di tipi organizza le classi in una struttura ad albero (o più in generale, un DAG), dove i tipi più generici (supertipi) si trovano in alto e vengono progressivamente raffinati da tipi più specifici (sottotipi).

💡 Scopo di una Gerarchia
L'obiettivo è creare un sistema di classi che condividono proprietà e comportamenti, permettendo di:
  • Riutilizzare il codice: La logica comune viene definita una sola volta nel supertipo.
  • Trattare oggetti diversi in modo uniforme: Possiamo scrivere codice che opera su un `Veicolo` senza sapere se si tratta di un'`Automobile` o di un `Camion` (polimorfismo).

2. Ereditarietà e Polimorfismo

L'ereditarietà è il meccanismo con cui un sottotipo (o classe derivata) acquisisce stato e comportamento da un supertipo (o classe base). Il sottotipo può poi:

  • Aggiungere nuovi metodi e campi.
  • Sovrascrivere (override) i metodi del supertipo per fornire un'implementazione più specifica.

Il polimorfismo (letteralmente "molte forme") è la conseguenza diretta dell'ereditarietà. Permette di trattare un oggetto di un sottotipo come se fosse un oggetto del suo supertipo. Questo è possibile perché un sottotipo, per definizione, deve avere tutti i metodi pubblici del suo supertipo.


// Supertipo (o classe base)
class Veicolo {
    public void muovi() {
        System.out.println("Il veicolo si muove.");
    }
}

// Sottotipo (o classe derivata)
class Automobile extends Veicolo {
    // Override del metodo del supertipo
    @Override
    public void muovi() {
        System.out.println("L'automobile corre sull'asfalto.");
    }

    // Aggiunta di un nuovo metodo
    public void accendiRadio() {
        System.out.println("Radio accesa.");
    }
}

// Esempio di Polimorfismo
Veicolo mioVeicolo = new Automobile(); // OK! Un'Automobile "è un" Veicolo

// Chiamata polimorfica: viene eseguito il metodo del tipo REALE (Automobile)
mioVeicolo.muovi(); // Stampa: "L'automobile corre sull'asfalto."

// ERRORE DI COMPILAZIONE: il compilatore vede solo il tipo APPARENTE (Veicolo)
// mioVeicolo.accendiRadio(); // Metodo non trovato in Veicolo

3. Le Interfacce

Un'interfaccia in Java è la forma più pura di astrazione sui tipi. È un contratto puro che definisce un insieme di comportamenti (metodi) che una classe può promettere di implementare.

Caratteristiche Principali

  • Definisce un tipo di dato, ma non fornisce implementazione per i suoi metodi (a meno che non siano `default` o `static`).
  • Non può avere variabili di istanza; può contenere solo costanti (`public static final`).
  • Non può essere istanziata direttamente con `new`.
  • Non ha uno stato concreto, quindi non ha né una Funzione di Astrazione (AF) né un Invariante di Rappresentazione (RI).
💡 Lo Scopo delle Interfacce
Le interfacce sono lo strumento principale per ottenere il disaccoppiamento. Permettono di definire un'API (un contratto) che nasconde un'intera famiglia di implementazioni, come abbiamo visto nell'esempio del `JSONizzatore` (Lezione 2), che implementava l'interfaccia `Serializzatore`. 

// Un'interfaccia definisce un contratto di "serializzabilità"
public interface Serializzabile {
    String toJson();
    String toXml();
}

// Una classe che "promette" di rispettare il contratto
public class Utente implements Serializzabile {
    private String nome;
    private int eta;

    // ... costruttore e altri metodi ...

    @Override
    public String toJson() {
        return "{ \"nome\": \"" + this.nome + "\", \"eta\": " + this.eta + " }";
    }

    @Override
    public String toXml() {
        return "" + this.nome + "" + this.eta + "";
    }
}

Ereditarietà Multipla di Tipo

A differenza delle classi, che supportano solo l'ereditarietà singola, una classe può implementare più interfacce. Questo le permette di "ereditare" più contratti e di essere trattata polimorficamente secondo diversi tipi.


// Una classe può essere sia Clonabile che Comparabile
public class Prodotto implements Cloneable, Comparable {
    // ... implementazione dei metodi di entrambe le interfacce ...
}

4. Le Classi Astratte

Una classe astratta si trova a metà strada tra un'interfaccia e una classe concreta. Fornisce una definizione di tipo e un'implementazione parziale.

Caratteristiche Principali

  • Può contenere sia metodi astratti (senza corpo, da implementare nelle sottoclassi) sia metodi concreti (con un corpo, ereditati dalle sottoclassi).
  • Può avere variabili di istanza (stato) che vengono ereditate dalle sottoclassi.
  • Non può essere istanziata direttamente con `new`.
  • Supporta solo l'ereditarietà singola (una classe può estendere al massimo una classe astratta).
💡 Lo Scopo delle Classi Astratte
Le classi astratte sono ideali per definire un comportamento e uno stato comune per una famiglia di classi strettamente correlate, lasciando alle sottoclassi il compito di definire i dettagli specifici. 

// Classe astratta che definisce lo stato e il comportamento comune di un animale
public abstract class Animale {
    private String nome;

    // Metodo concreto, ereditato da tutte le sottoclassi
    public String getNome() {
        return this.nome;
    }

    // Metodo astratto, ogni sottoclasse DEVE implementarlo
    public abstract String emettiVerso();
}

// Classe concreta che estende la classe astratta
public class Cane extends Animale {
    @Override
    public String emettiVerso() {
        return "Bau!";
    }
}

public class Gatto extends Animale {
    @Override
    public String emettiVerso() {
        return "Miao!";
    }
}

5. Interfaccia o Classe Astratta? La Scelta Giusta

La scelta tra un'interfaccia e una classe astratta è una decisione di design fondamentale. Ecco una guida pratica:

Criterio Usa un'Interfaccia se... Usa una Classe Astratta se...
Relazione tra le classi ...le classi che implementano il contratto sono non correlate o possono appartenere a gerarchie diverse (es. `Comparable`, `Serializable`). ...stai costruendo una famiglia di classi strettamente correlate che condividono molto codice (es. `Grafico`, `FormaGeometrica`).
Condivisione di Stato ...non hai bisogno di condividere variabili di istanza. Le interfacce (pre-Java 8) non possono avere stato. ...le sottoclassi devono condividere uno stato comune (campi `private` o `protected`).
Condivisione di Codice ...vuoi solo definire un contratto di comportamento, senza fornire un'implementazione di default (anche se Java 8+ permette i `default methods`). ...vuoi fornire un'implementazione di base per alcuni metodi, lasciando altri come astratti.
Ereditarietà Multipla ...una classe ha bisogno di "ereditare" più tipi/contratti. ...l'ereditarietà singola è sufficiente (poiché una classe può estendere una sola altra classe).
⚠️ Preferisci le Interfacce alle Classi Astratte
Come regola generale, se hai dubbi, preferisci le interfacce. Le interfacce offrono maggiore flessibilità e disaccoppiamento. Puoi sempre decidere in un secondo momento di fornire una classe astratta di base che implementa l'interfaccia per aiutare gli sviluppatori, ma partire dall'interfaccia mantiene le tue opzioni aperte.

6. Struttura Tipica di una Gerarchia

Una gerarchia ben progettata in Java spesso combina entrambi gli strumenti in una struttura a più livelli per massimizzare flessibilità e riuso.

  1. Al vertice c'è un'interfaccia: Definisce il contratto pubblico e il tipo più generale. Il codice client dovrebbe dipendere da questa.
  2. Sotto, una classe astratta (opzionale): Fornisce un'implementazione di base per i metodi più comuni, gestendo stato e logica condivisi.
  3. Infine, le classi concrete: Estendono la classe astratta (o implementano direttamente l'interfaccia) per fornire implementazioni complete e specializzate. Possono essere implementazioni alternative (es. `ArrayList` vs `LinkedList`) o estensioni che aggiungono nuove funzionalità.
