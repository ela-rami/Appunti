1. Introduzione alle Gerarchie di Tipi

Nello sviluppo software, spesso ci troviamo a dover modellare un sistema di classi che condividono proprietà e comportamenti. L'obiettivo è creare una "famiglia di tipi" che rifletta le relazioni del mondo reale e consenta la scrittura di codice più flessibile e riutilizzabile.

Una **gerarchia di tipi** è una struttura organizzativa dove un tipo generale (supertype) è raffinato da tipi più specifici (subtypes). Questa raffinazione può avvenire in due modi:

  • Fornendo implementazioni alternative di un comportamento già definito (es. un `DensePoly` e un `SparsePoly` che implementano entrambi `Poly`).
  • Aggiungendo nuovi metodi o funzionalità che sono specifici del subtype (es. un `MaxIntSet` che aggiunge il metodo `max()` a un `IntSet`).

Il meccanismo fondamentale che abilita la creazione e l'uso flessibile di queste gerarchie in Java è l'**ereditarietà**.

2. L'Ereditarietà: Base delle Gerarchie

L'**ereditarietà** è un pilastro dell'OOP che permette a una classe (sottoclasse o classe derivata) di ereditare proprietà e comportamenti da un'altra classe (superclasse o classe base). Questo favorisce il riuso del codice e stabilisce una relazione "is-a" (es. "un Cane *è un* Animale").

Quando si definisce una sottoclasse, si specificano solo le **differenze** rispetto alla superclasse: nuovi metodi, nuovi campi o l'override di metodi esistenti per modificarne il comportamento. La sintassi Java per l'ereditarietà è `class SubClass extends SuperClass { ... }`.


// Superclasse generica
public class Animal {
    protected String species;

    public Animal(String species) {
        this.species = species;
    }

    public void makeSound() {
        System.out.println("Generic animal sound");
    }
}

// Sottoclasse che eredita e specializza
public class Dog extends Animal {
    public Dog(String name) {
        super("Canis familiaris"); // Chiama il costruttore della superclasse
        // this.name = name; // Potrebbe avere un campo name specifico del cane
    }

    @Override // Sovrascrive il comportamento della superclasse
    public void makeSound() {
        System.out.println("Woof woof!");
    }

    public void fetch() { // Nuovo metodo specifico di Dog
        System.out.println("Fetching the ball!");
    }
}

3. Le Interfacce

In Java, le **interfacce** sono un concetto fondamentale per definire i contratti e le gerarchie di tipi. Un'interfaccia è un "contratto" che una classe può promettere di rispettare.

Caratteristiche delle Interfacce

  • **Definizione di Tipo Puro:** Un'interfaccia fornisce solo la **definizione del tipo**, senza alcuna implementazione concreta (prima di Java 8).
  • **Metodi Astratti:** Contengono solo firme di metodi astratti (senza corpo). 
    
public interface Drivable {
    void drive(); // Metodo astratto (implicito)
    void stop();
}
  • **Costanti:** Possono contenere solo costanti (`public static final`, implicito).
  • **Assenza di Stato:** Non possono avere variabili di istanza (campi non `static` e non `final`). Questo significa che non hanno uno "stato concreto" proprio, né un invariante di rappresentazione diretto.
  • **Java 8+:** Possono contenere `default methods` (metodi con implementazione di default) e `static methods` (metodi di utilità legati all'interfaccia, non all'istanza).

Scopo delle Interfacce

  • Definire un Contratto (API): Costituiscono l'API pubblica di un componente, specificando il comportamento atteso senza rivelare i dettagli interni.
  • Nascondere Famiglie di Tipi: Permettono ai client di programmare verso un'interfaccia (es. `List`) senza dipendere da una specifica implementazione (es. `ArrayList` o `LinkedList`). Questo facilita il disaccoppiamento.
  • Supportare Dependency Inversion Principle (DIP): Le interfacce sono la chiave per far sì che i moduli di alto livello dipendano dalle astrazioni, non dalle implementazioni concrete.
  • Ereditarietà Multipla di Tipo: Una classe può implementare più interfacce, ereditando le definizioni di comportamento da ciascuna (cosa non possibile con l'ereditarietà di classi in Java).

public class Car implements Drivable { // La classe Car promette di implementare Drivable
    @Override
    public void drive() {
        System.out.println("Car is driving.");
    }

    @Override
    public void stop() {
        System.out.println("Car stopped.");
    }
}

4. Le Classi Astratte

Una **classe astratta** è un compromesso tra un'interfaccia e una classe concreta. Non può essere istanziata direttamente, ma può fornire un'implementazione parziale e definire metodi che le sottoclassi devono implementare.

Caratteristiche delle Classi Astratte

  • **Implementazione Parziale:** Possono avere metodi **concreti** (con implementazione) e metodi **astratti** (senza implementazione, che le sottoclassi concrete *devono* implementare).
  • **Campi:** Possono avere variabili di istanza (campi non `static` e non `final`), che rappresentano uno stato condiviso tra le sottoclassi.
  • **Costruttori:** Possono avere costruttori, sebbene non possano essere chiamati direttamente per creare istanze (possono essere chiamati dalle sottoclassi con `super()`).

// Classe astratta per un'entità con ID
public abstract class Entity {
    protected int id; // Campo di istanza

    public Entity(int id) {
        this.id = id;
    }

    public int getId() { // Metodo concreto
        return id;
    }

    public abstract void process(); // Metodo astratto: deve essere implementato dalle sottoclassi
}

// Sottoclasse concreta
public class ConcreteEntity extends Entity {
    public ConcreteEntity(int id) {
        super(id);
    }

    @Override
    public void process() { // Implementazione del metodo astratto
        System.out.println("Processing entity " + this.id);
    }
}

5. Interfacce vs. Classi Astratte: Quando Usarle?

La scelta tra interfaccia e classe astratta è cruciale per un buon design.

⚖️ Regola Decisionale
  • Usa una **Classe Astratta** quando:
    • Vuoi costruire una famiglia di tipi dove le classi condividono una **parte dello stato** (campi `protected` o `private`).
    • Vuoi fornire un'**implementazione comune di default** che le sottoclassi possono (ma non devono per forza) sovrascrivere.
    • Vuoi avere metodi `non-static` e `non-final` che implementano una logica di base.
    • C'è una forte relazione "is-a" e una gerarchia di specializzazione ben definita.
  • Usa un'**Interfaccia** quando:
    • Vuoi definire un **contratto** (API) senza alcuna implementazione.
    • I tipi che implementeranno il contratto possono essere **totalmente non correlati** tra loro (es. `Comparable`, `Cloneable`).
    • Vuoi sfruttare il vantaggio dell'**ereditarietà multipla** (una classe può implementare più interfacce).
    • Vuoi astrarre un "comportamento" che può essere applicato a diverse classi, indipendentemente dalla loro posizione nella gerarchia di ereditarietà.
Esempio: La Gerarchia `IntSet`

La gerarchia `IntSet` (vista nelle slide) è un ottimo esempio pratico:

  1. `IntSet` (Interfaccia): Definisce il contratto puro di un set di interi (`insert`, `remove`, `size`, `iterator`, etc.). Nessuna implementazione.
  2. `IntSetImpl` (Classe Astratta, non sempre presente): Potrebbe essere una classe astratta che fornisce un'implementazione parziale comune (es. gestendo il `currentSize` e i controlli `invariantOK()` con `assert` per tutte le implementazioni).
  3. `UnorderedIntSet` (Classe Concreta): Estende `IntSetImpl` e implementa `IntSet` usando una rappresentazione `Vector` per un set non ordinato.
  4. `MaxIntSet` (Classe Concreta): Estende `UnorderedIntSet` e aggiunge un campo `highestValue` e un metodo `max()`, sovrascrivendo `insert` e `remove` per mantenere `highestValue` aggiornato.

Questo esempio mostra come interfacce e classi astratte collaborino per definire l'astrazione e fornire implementazioni riutilizzabili o specializzate.

6. Struttura Tipica di una Gerarchia

Una gerarchia ben progettata segue spesso questo schema:

  1. **Interfacce:** In cima, per definire tipi molto generali (il "cosa").
  2. **Classi Astratte:** Sotto le interfacce, per fornire implementazioni parziali e uno stato comune condiviso per una famiglia di tipi correlati.
  3. **Classi Concrete:** In basso, per fornire implementazioni complete. Possono essere:
    • **Implementazioni Alternative:** Diversi modi di realizzare la stessa interfaccia o classe astratta (es. `ArrayList` vs `LinkedList`).
    • **Estensioni:** Aggiunta di nuove funzionalità o specializzazioni (es. `MaxIntSet` aggiunge `max()`).

Questa struttura promuove il riuso, la flessibilità e il disaccoppiamento, pilastri fondamentali del design orientato agli oggetti.
