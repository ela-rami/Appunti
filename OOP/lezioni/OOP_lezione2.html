1. Design by Contract (DbC)

Il **Design by Contract (DbC)** è una metodologia di progettazione software che vede l'interazione tra i componenti software (classi, metodi) come un **contratto formale**. Questo approccio mira a creare software più robusto, documentato e verificabile.

Un contratto tra un metodo (il "fornitore") e chi lo chiama (il "cliente") si basa su obblighi e benefici reciproci:

  • Il Cliente (Chi chiama il metodo): Ha l'obbligo di rispettare le pre-condizioni. Se lo fa, ha il beneficio di ottenere i risultati promessi dalle post-condizioni.
  • Il Fornitore (Il metodo): Ha il beneficio di poter assumere che le pre-condizioni siano valide. In cambio, ha l'obbligo di garantire le post-condizioni al termine della sua esecuzione.

Gli Elementi del Contratto di un Metodo

  1. Pre-condizioni (`REQUIRES`): Proprietà che devono essere vere **prima** che il metodo venga eseguito. Sono responsabilità del chiamante. Se una pre-condizione è violata, il comportamento del metodo è indefinito (può fare qualsiasi cosa).
  2. Post-condizioni (`EFFECTS`, `RETURNS`): Proprietà che il metodo garantisce essere vere **al termine** della sua esecuzione, a patto che le pre-condizioni fossero soddisfatte. Sono responsabilità del metodo.
  3. Effetti collaterali (`MODIFIES`): Una parte importante delle post-condizioni che specifica quali oggetti passati come parametro (o lo stato dell'oggetto stesso) vengono modificati.
💡 Specifica vs. Implementazione
Il contratto definisce il **cosa** (what) fa un metodo, non il **come** (how) lo fa. Questo separa nettamente l'interfaccia pubblica dall'implementazione privata, un pilastro dell'incapsulamento.

2. Astrazioni Parziali e Totali

Grazie ai contratti, possiamo classificare le astrazioni (i metodi) in due categorie.

  • Un'astrazione totale è una funzione che è definita per tutti i possibili input che rispettano il loro tipo. Non ha pre-condizioni aggiuntive.
  • Un'astrazione parziale è una funzione che ha delle pre-condizioni restrittive. È definita solo per un sottoinsieme degli input possibili.
Esempio: Fattoriale

La funzione matematica del fattoriale è definita solo per interi non negativi. Un metodo `factorial(int n)` che ha la pre-condizione `REQUIRES n >= 0` è un'astrazione parziale. Non ci dice cosa succede se viene chiamato con `factorial(-3)`.

Le astrazioni parziali sono "pericolose" perché scaricano sul client la responsabilità di garantire le pre-condizioni. L'obiettivo della programmazione robusta è trasformare, dove possibile, le astrazioni parziali in astrazioni totali, gestendo esplicitamente anche i casi "sbagliati".

3. Strategie di Gestione degli Errori

Quando un client viola una pre-condizione, come possiamo gestire l'errore? Ci sono principalmente due approcci, di cui uno è fortemente sconsigliato.

Approccio 1: Estendere il Set di Risultati (SCONSIGLIATO)

Questa strategia consiste nel "nascondere" l'errore nel valore di ritorno. Ad esempio, un metodo `factorial(n)` potrebbe restituire `-1` se `n` è negativo.

⚠️ Perché è una pessima idea?
  • Insicuro: Il client potrebbe dimenticarsi di controllare il valore speciale (`-1`) e usarlo in calcoli successivi, propagando l'errore in modo silenzioso e portando a bug difficilissimi da scovare.
  • Limitato: Non sempre è possibile trovare un valore "speciale" che non sia già un risultato valido. Ad esempio, un metodo che restituisce un `Object` può restituire qualsiasi cosa.
  • Codice Sporco: Obbliga il client a scrivere codice pieno di `if` per controllare i valori di ritorno, mescolando la logica di business con la logica di gestione degli errori.

Approccio 2: Segnalazione Esplicita dell'Errore (CONSIGLIATO)

Questa strategia prevede di interrompere il flusso normale del programma e segnalare esplicitamente che si è verificata una condizione eccezionale. Questo trasforma l'astrazione parziale in un'astrazione totale che ha due possibili esiti: un risultato normale o una segnalazione d'errore.

In Java, questo si implementa con due meccanismi principali: le eccezioni e le asserzioni.

4. Le Eccezioni in Java

Le eccezioni sono il meccanismo principale di Java per gestire errori e situazioni anomale a runtime, specialmente quelle causate da un uso scorretto di un'API da parte del client.

Cosa sono?

Un'eccezione è un oggetto che rappresenta un evento anomalo. Quando viene "lanciata" (`throw`), interrompe il normale flusso di esecuzione e passa il controllo al più vicino gestore di eccezioni (`catch`) compatibile.

  • Checked Exceptions: Ereditano da `Exception` ma non da `RuntimeException`. Rappresentano condizioni eccezionali da cui un client **può ragionevolmente riprendersi** (es. `FileNotFoundException`, `IOException`). Il compilatore **obbliga** a gestirle: o con un blocco `try-catch` o dichiarandole nella firma del metodo con `throws`.
  • Unchecked Exceptions: Ereditano da `RuntimeException` (o `Error`). Rappresentano **errori di programmazione** (bug) che non dovrebbero accadere in un programma corretto (es. `NullPointerException`, `IndexOutOfBoundsException`). Il compilatore non obbliga a gestirle.

Come si usano nei Contratti

Le eccezioni sostituiscono la clausola `REQUIRES` nel contratto. Un metodo non dice più "richiedo che `a` non sia nullo", ma "se `a` è nullo, lancio `NullPointerException`".


/**
 * Cerca un elemento in un array.
 *
 * @param array L'array in cui cercare.
 * @param element L'elemento da trovare.
 * @return L'indice dell'elemento.
 * @throws NullPointerException se l'array è nullo.
 * @throws NoSuchElementException se l'elemento non viene trovato.
 */
public static int search(int[] array, int element) throws NoSuchElementException {
    // 1. Controllo della pre-condizione con un'eccezione
    if (array == null) {
        throw new NullPointerException("L'array di input non può essere nullo.");
    }

    for (int i = 0; i < array.length; i++) {
        if (array[i] == element) {
            return i; // Flusso normale
        }
    }

    // 2. Segnalazione di un'altra condizione eccezionale
    throw new NoSuchElementException("Elemento non trovato nell'array.");
}

5. Le Asserzioni in Java

Le asserzioni sono uno strumento di debugging per il programmatore. Servono a verificare le **assunzioni** che il programmatore fa sulla correttezza del proprio codice.

Sintassi e Comportamento

Si scrivono con la parola chiave `assert`.


assert (x > 0) : "x deve essere positivo, ma è " + x;

Se la condizione è `true`, non succede nulla. Se è `false`, viene lanciato un `AssertionError`, che tipicamente causa l'arresto del programma. Fondamentalmente, le asserzioni possono essere **disabilitate** dalla JVM (e lo sono di default). Quando disabilitate, non hanno alcun impatto sulle prestazioni.

Quando Usarle?

Le asserzioni sono perfette per verificare le "promesse" interne al codice, ovvero che il *vostro* codice stia funzionando come previsto.

  • Invarianti di Rappresentazione (RI): Per controllare che lo stato interno di un oggetto sia sempre valido all'inizio e alla fine di un metodo pubblico.
  • Post-condizioni: Per verificare che un metodo abbia prodotto il risultato atteso.
  • Pre-condizioni di metodi `private`:** Poiché un metodo privato è chiamato solo dal codice della stessa classe, il programmatore ha il pieno controllo sugli input e può usare `assert` per assicurarsi che li stia passando correttamente.
  • Punti del codice che non dovrebbero mai essere raggiunti (es. il ramo `default` di uno `switch` che copre tutti i casi possibili di un enum).

private void setBalance(double newBalance) {
    // Un metodo privato. Posso usare assert per la pre-condizione
    // perché sono io (la classe) l'unico a chiamarlo.
    assert newBalance >= 0 : "Il saldo non può diventare negativo";
    
    this.balance = newBalance;
    
    // Controllo l'invariante di rappresentazione alla fine
    assert this.invariantOK(); 
}

6. Eccezioni vs. Asserzioni: La Scelta Giusta

La regola d'oro per decidere se usare un'eccezione o un'asserzione è semplice:

⚖️ Regola Decisionale
  • Usa le Eccezioni per violazioni del contratto di metodi pubblici. Sono errori che un *client* può commettere. Devono funzionare anche in produzione.
  • Usa le Asserzioni per verificare assunzioni sul tuo codice interno. Sono *bug* che tu, come programmatore, devi risolvere. Possono (e dovrebbero) essere disattivate in produzione.

In pratica: un'eccezione dice "Tu (client) hai sbagliato a usare il mio codice". Un'asserzione fallita dice "Io (programmatore) ho sbagliato a scrivere il mio codice".


public class BankAccount {
    private double balance;

    // ... invarianti e costruttore ...

    /**
     * Preleva una somma dal conto.
     * @param amount La somma da prelevare. Deve essere positiva.
     * @throws IllegalArgumentException se 'amount' è negativo.
     * @throws InsufficientFundsException se il saldo non è sufficiente.
     */
    public void withdraw(double amount) throws InsufficientFundsException {
        // CONTROLLO DI PRE-CONDIZIONE PUBBLICA -> ECCEZIONE
        if (amount < 0) {
            throw new IllegalArgumentException("L'importo da prelevare non può essere negativo.");
        }
        
        // LOGICA DI BUSINESS
        if (this.balance < amount) {
            throw new InsufficientFundsException("Fondi insufficienti", this.balance, amount);
        }

        this.balance -= amount;
        
        // CONTROLLO DI POST-CONDIZIONE/INVARIANTE INTERNO -> ASSERZIONE
        assert this.balance >= 0;
    }
}
