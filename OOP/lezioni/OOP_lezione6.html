1. L'Importanza dell'LSP

Nelle lezioni precedenti abbiamo visto come l'ereditarietà e il polimorfismo ci permettano di creare gerarchie di tipi flessibili. Tuttavia, l'ereditarietà non è solo un meccanismo per riutilizzare il codice. È prima di tutto un meccanismo per definire una relazione di sottotipo comportamentale.

Se una classe `Sottotipo` estende `Supertipo`, implicitamente dichiariamo che "un `Sottotipo` è un `Supertipo`". Questo significa che ogni istanza di `Sottotipo` dovrebbe potersi comportare come un'istanza di `Supertipo` senza sorprendere il client o rompere il programma.

Il Principio di Sostituzione di Liskov (LSP), formulato da Barbara Liskov, fornisce le regole formali per garantire che questa relazione di sottotipo sia semanticamente corretta.

⚠️ Il Rischio
Una violazione dell'LSP porta a gerarchie fragili, codice imprevedibile e bug difficili da scovare. Il compilatore Java può verificare solo la correttezza sintattica (le firme dei metodi), ma non quella comportamentale. Garantire l'LSP è una responsabilità del programmatore.

2. Definizione del Principio

La definizione formale dell'LSP può essere espressa così:

💡 Principio di Sostituzione di Liskov
"Se per ogni oggetto `o1` di tipo `S` esiste un oggetto `o2` di tipo `T` tale che per tutti i programmi `P` definiti in termini di `S`, il comportamento di `P` non cambia quando `o1` è sostituito con `o2`, allora `T` è un sottotipo di `S`."

In parole più semplici: i sottotipi devono essere sostituibili ai loro supertipi senza alterare la correttezza del programma. Un client che usa un riferimento a un `Supertipo` non dovrebbe nemmeno accorgersi (o preoccuparsi) se l'oggetto reale che sta manipolando è un'istanza del `Supertipo` o di uno qualsiasi dei suoi `Sottotipi`.

3. Caso di Studio: Rettangolo e Quadrato

L'esempio più classico di violazione dell'LSP è la relazione tra `Rettangolo` e `Quadrato`. Intuitivamente, un quadrato "è un" rettangolo. Proviamo a modellarlo con l'ereditarietà.


public class Rettangolo {
    protected int base;
    protected int altezza;

    public void setBase(int base) { this.base = base; }
    public void setAltezza(int altezza) { this.altezza = altezza; }

    // ... altri metodi come getBase, getAltezza, area ...
}

public class Quadrato extends Rettangolo {
    // Un quadrato deve avere base e altezza uguali.
    // Tentiamo di forzare questo invariante sovrascrivendo i setter.

    @Override
    public void setBase(int lato) {
        super.setBase(lato);
        super.setAltezza(lato); // Violazione in agguato!
    }

    @Override
    public void setAltezza(int lato) {
        super.setAltezza(lato);
        super.setBase(lato); // Violazione in agguato!
    }
}

3.1. Il Problema Comportamentale

A prima vista, il codice sembra corretto. Ma cosa succede quando un client usa questi oggetti in modo polimorfico?


public class Client {
    public void unaFunzione(Rettangolo r) {
        // Il contratto implicito di questo metodo si aspetta che, dopo aver impostato
        // base e altezza, queste rimangano indipendenti.
        r.setBase(5);
        r.setAltezza(4);

        // Mi aspetto che l'area sia 5 * 4 = 20.
        assert r.area() == 20;
    }

    public static void main(String[] args) {
        Client c = new Client();
        Rettangolo rettangolo = new Rettangolo();
        Rettangolo quadrato = new Quadrato();

        c.unaFunzione(rettangolo); // OK, l'assert passa (area è 20).
        c.unaFunzione(quadrato);   // ERRORE! L'assert fallisce.
    }
}

Quando `unaFunzione` riceve un `Quadrato`, succede questo:

  1. `r.setBase(5)` imposta sia la base che l'altezza a 5. Il quadrato diventa 5x5.
  2. `r.setAltezza(4)` imposta sia l'altezza che la base a 4. Il quadrato diventa 4x4.
  3. L'area calcolata è `4 * 4 = 16`, non 20. L'asserzione fallisce.
⚠️ Violazione del Contratto
Il problema non è che il `Quadrato` si comporta in modo errato per un quadrato, ma che si comporta in modo diverso da un `Rettangolo`. Il metodo `setBase` del `Rettangolo` ha una post-condizione implicita: "la base cambia, l'altezza rimane invariata". Il metodo `setBase` del `Quadrato` viola questa post-condizione, alterando anche l'altezza. Per questo, un `Quadrato` non è un sottotipo comportamentale corretto di `Rettangolo`.

4. Le Regole dell'LSP

Per essere un sottotipo corretto, una classe `SUB` che estende `SUPER` deve rispettare tre insiemi di regole.

4.1. Regola della Firma (Garantita da Java)

Il sottotipo deve avere tutti i metodi del supertipo, con firme compatibili.

  • I tipi dei parametri devono essere identici (o più generali nel sottotipo - controvarianza, non supportato da Java).
  • Il tipo di ritorno può essere più specifico nel sottotipo (covarianza).
  • Il sottotipo può lanciare meno eccezioni (o eccezioni più specifiche) rispetto al metodo sovrascritto, ma non di nuove o più generiche (checked).

Il compilatore Java si occupa di far rispettare questa regola.

4.2. Regola dei Metodi (Pre/Post-condizioni)

Questa è la regola comportamentale chiave, non garantita dal compilatore.

💡 "Richiedi meno, prometti di più"
  • Pre-condizioni: Un metodo sovrascritto nel sottotipo non può avere pre-condizioni più forti (più restrittive) di quelle del supertipo. Può averle uguali o più deboli.
    Formalmente: \( \text{pre}_{SUPER}(x) \implies \text{pre}_{SUB}(x) \)
  • Post-condizioni: Un metodo sovrascritto nel sottotipo non può avere post-condizioni più deboli (promettere di meno) di quelle del supertipo. Può averle uguali o più forti.
    Formalmente: \( \text{post}_{SUB}(x) \implies \text{post}_{SUPER}(x) \)

Nel nostro esempio, il `Quadrato` viola la regola delle post-condizioni. La post-condizione di `Rettangolo.setBase` è \( \text{this.base} = b \land \text{this.altezza} = \text{altezza}' \). Quella di `Quadrato.setBase` è \( \text{this.base} = b \land \text{this.altezza} = b \). La seconda non implica la prima (perché cambia anche l'altezza).

4.3. Regola delle Proprietà (Invarianti)

Un sottotipo deve preservare tutte le proprietà e gli invarianti del suo supertipo.

Esempio: `FatIntSet` vs. `ThinIntSet`

Immaginiamo una classe `FatIntSet` il cui invariante è "l'insieme non può mai essere vuoto". Se creiamo una sottoclasse `ThinIntSet` che estende `FatIntSet` ma permette all'insieme di diventare vuoto tramite un'operazione `remove()`, allora `ThinIntSet` non è un sottotipo valido di `FatIntSet` perché viola il suo invariante fondamentale.

Anche la relazione `Rettangolo`/`Quadrato` viola questa regola. Un invariante di `Rettangolo` è che "la base e l'altezza sono proprietà indipendenti". Il `Quadrato` invalida questa proprietà, legandole insieme.

5. Conclusioni e Alternative

Il Principio di Sostituzione di Liskov ci insegna che l'ereditarietà va usata per modellare una relazione "è un" comportamentale, non solo tassonomica.

Cosa fare quando l'LSP è violato?

Se un sottotipo non può rispettare il contratto del suo supertipo, l'ereditarietà è la scelta sbagliata. Le alternative sono:

  1. Creare una gerarchia diversa: Magari `FormaGeometrica` è il supertipo, e `Rettangolo` e `Quadrato` sono due sottotipi fratelli, non in relazione padre-figlio.
  2. Usare la Composizione e la Delegazione: Invece di `Quadrato extends Rettangolo`, la classe `Quadrato` potrebbe *contenere* un'istanza di un'altra classe (es. `Lato`) e delegare a essa i calcoli, senza ereditare comportamenti indesiderati.
💡 Regola Pratica
L'ereditarietà è uno strumento potente ma anche rigido. Se hai dubbi sulla validità comportamentale di una relazione "is-a", preferisci la composizione all'ereditarietà. È una soluzione più flessibile e meno soggetta a violazioni dell'LSP.
