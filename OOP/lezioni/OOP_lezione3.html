1. Cos'è un Tipo di Dato Astratto (ADT)?

Un Tipo di Dato Astratto (ADT) è un modello matematico per un tipo di dato. È definito dal suo comportamento (le operazioni che si possono eseguire) e dal suo valore (lo stato che può assumere), dal punto di vista dell'utente (il client). Un ADT si concentra sul "cosa" un tipo di dato rappresenta e fa, ignorando completamente il "come" viene implementato.

L'obiettivo è creare nuovi tipi di dato che estendono il linguaggio, permettendo di modellare il dominio del problema in modo più naturale. In Java, gli ADT sono tipicamente realizzati tramite classi e interfacce.

💡 Esempi di ADT
  • Insieme (Set): Un ADT che rappresenta una collezione di elementi unici. Le sue operazioni sono `add`, `remove`, `contains`, `size`.
  • Pila (Stack): Un ADT che rappresenta una collezione LIFO (Last-In, First-Out). Le sue operazioni sono `push`, `pop`, `peek`.
  • Polinomio (Poly): Un ADT che rappresenta un'espressione matematica. Le operazioni sono `add`, `multiply`, `degree`.

La caratteristica fondamentale di un ADT è che le sue operazioni sono definite in termini del modello astratto, non dei dettagli implementativi.

2. La Specifica di un ADT

Per definire formalmente un ADT, dobbiamo specificare due componenti principali, che insieme formano il suo contratto pubblico.

Lo Stato Astratto

Descrive l'insieme dei possibili valori che un'istanza dell'ADT può assumere, in termini puramente matematici o logici.

  • Per un `IntSet`, lo stato astratto è "un qualsiasi insieme finito di numeri interi".
  • Per un `Poly`, lo stato astratto è "un qualsiasi polinomio a coefficienti interi e esponenti non negativi".

Il Protocollo (le Operazioni)

È l'insieme delle operazioni (metodi) che possono essere eseguite sull'ADT. Ogni operazione è definita dal suo contratto (pre-condizioni, post-condizioni, `@throws`), che si riferisce sempre allo stato astratto, mai a quello concreto.


// Esempio di contratto per il metodo insert di un IntSet

/**
 * Aggiunge un intero all'insieme.
 * 
 * MODIFIES: this
 * EFFECTS: se x non è già in this, lo aggiunge.
 *          Altrimenti, non fa nulla.
 *
 * @param x l'intero da aggiungere.
 */
public void insert(int x);

Nota come la specifica parli di "aggiungere all'insieme", un concetto astratto, senza menzionare array, liste o altre strutture dati.

3. L'Implementazione di un ADT

L'implementazione è il "come". Si tratta di scegliere una struttura dati concreta per rappresentare lo stato astratto e di scrivere il codice per i metodi. Per ragionare sulla correttezza di un'implementazione, introduciamo due concetti cruciali: la Funzione di Astrazione e l'Invariante di Rappresentazione.

3.1. Funzione di Astrazione (AF)

La Funzione di Astrazione (AF) è una mappa che definisce come lo stato concreto (la rappresentazione interna) viene interpretato per rappresentare uno stato astratto. È il "ponte" che collega il mondo dell'implementazione al mondo del modello matematico.

AF : Stato Concreto \(\to\) Stato Astratto
Esempio: IntSet implementato con un `Vector`

Stato Concreto: Una variabile di istanza `private Vector elements;`. I suoi valori possono essere `null`, `[]`, `[1, 2]`, `[2, 1]`, `[1, 2, 1]`, ecc.

Stato Astratto: Un insieme matematico di interi. I suoi valori sono `{}`, `{1}`, `{1, 2}`, ecc.

Funzione di Astrazione (AF):

`AF(c) = {c.elements.get(i) | 0 <= i < c.elements.size()}`

Questa formula ci dice che, dato un oggetto concreto `c`, il suo valore astratto è l'insieme di tutti gli elementi contenuti nel suo `Vector` `elements`. Grazie all'AF, possiamo interpretare diversi stati concreti:

  • AF([1, 2]) \(\to\) `{1, 2}`
  • AF([2, 1]) \(\to\) `{1, 2}` (lo stesso stato astratto!)
  • AF([1, 2, 1]) \(\to\) `{1, 2}` (gli insiemi non hanno duplicati)

La funzione di astrazione è spesso molti-a-uno: più stati concreti possono rappresentare lo stesso stato astratto. Questo è normale e desiderabile, in quanto dà libertà all'implementatore.

3.2. Invariante di Rappresentazione (RI)

Non tutti i valori possibili dello stato concreto sono "validi" per rappresentare uno stato astratto. L'Invariante di Rappresentazione (RI) è una proprietà che definisce quali stati concreti sono ben formati. L'RI deve essere vero per ogni istanza della classe prima e dopo l'esecuzione di ogni metodo pubblico.

RI : Stato Concreto \(\to\) {true, false}
Esempio: IntSet implementato con un `Vector`

Quali sono le proprietà che il nostro `Vector` `elements` deve sempre avere per rappresentare correttamente un insieme?

Invariante di Rappresentazione (RI):

  1. `elements` non deve essere `null`.
  2. `elements` non deve contenere elementi `null`.
  3. `elements` non deve contenere duplicati.

Lo stato concreto `[1, 2, 1]` viola la terza regola dell'RI, quindi è uno stato invalido che la nostra implementazione deve evitare di produrre. Uno stato `null` viola la prima regola. Invece, `[1, 2]` e `[2, 1]` sono entrambi stati concreti validi che rispettano l'RI.

L'RI è uno strumento potentissimo per il programmatore. Viene tipicamente controllato tramite un metodo `private boolean checkRep()` o `invariantOK()`, invocato con `assert` all'inizio e alla fine di ogni metodo pubblico per trovare bug durante lo sviluppo.


private boolean invariantOK() {
    if (elements == null) return false;
    // Controlla che non ci siano duplicati
    Set uniqueElements = new HashSet<>(elements);
    return uniqueElements.size() == elements.size();
}

public void insert(int x) {
    assert invariantOK(); // Controlla RI all'inizio

    // ... corpo del metodo ...
    
    assert invariantOK(); // Controlla RI alla fine
}

3.3. AF e RI: Il Ponte tra Astratto e Concreto

🔍 AF vs. RI: Una Sintesi
  • L'Invariante di Rappresentazione (RI) filtra gli stati concreti, separando quelli "buoni" (validi) da quelli "cattivi" (invalidi).
  • La Funzione di Astrazione (AF) si applica solo agli stati concreti "buoni" (che soddisfano l'RI) e li mappa ai loro corrispondenti valori astratti.

4. L'Importanza dell'Incapsulamento (Representation Exposure)

Un ADT, per essere robusto e manutenibile, NON DEVE MAI ESPORRE LA SUA RAPPRESENTAZIONE INTERNA. Questo significa che le variabili di istanza devono essere `private` e nessun metodo deve restituire un riferimento diretto a un oggetto mutabile interno.

Cosa succede se si espone la rappresentazione?

Se un client ottiene un riferimento diretto allo stato concreto (es. al `Vector` `elements` del nostro `IntSet`), possono accadere due disastri:

  1. Il client può rompere l'Invariante di Rappresentazione (RI): Potrebbe aggiungere duplicati o elementi `null` al `Vector`, portando l'oggetto in uno stato corrotto e causando comportamenti imprevedibili nei metodi successivi.
  2. Si crea un forte accoppiamento: Il client ora dipende dalla specifica implementazione (`Vector`). Se in futuro volessimo cambiare la rappresentazione interna di `IntSet` (es. usando un `HashSet` per maggiore efficienza), saremmo costretti a modificare anche tutto il codice del client che faceva affidamento sul `Vector`. L'astrazione è andata perduta.
⚠️ Attenzione all'esposizione implicita (Aliasing)

Anche un metodo che sembra innocuo può esporre la rappresentazione. Considera questo metodo in una classe `Team`:


public class Team {
    private List players;
    
    public List getPlayers() {
        return this.players; // PERICOLO! Restituisce un riferimento all'oggetto mutabile interno.
    }
}

// Codice client
Team myTeam = new Team();
List teamPlayers = myTeam.getPlayers();
teamPlayers.clear(); // Ora il team non ha più giocatori! L'invariante è stato rotto dall'esterno.

Soluzione: Restituire sempre una copia difensiva degli oggetti mutabili interni.


public List getPlayers() {
    return new ArrayList<>(this.players); // Restituisce una copia, non l'originale.
}

Clonazione: Shallow vs. Deep Copy

Un altro meccanismo per creare copie di oggetti è il metodo .clone(), ereditato da Object. È fondamentale capire la differenza tra:

  • Shallow Copy (Copia Superficiale): Crea un nuovo oggetto ma copia solo i riferimenti ai campi interni. Se i campi sono oggetti mutabili, sia la copia che l'originale punteranno agli stessi oggetti interni, rompendo l'incapsulamento. È il comportamento di default di Object.clone().
  • Deep Copy (Copia Profonda): Crea un nuovo oggetto e copia ricorsivamente anche tutti gli oggetti interni, garantendo che l'originale e la copia siano completamente indipendenti. È spesso necessaria per ADT con stato mutabile.
