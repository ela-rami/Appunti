Step 1: Definire Enum e ADT di Base (Immutabili)

Iniziamo analizzando le prime frasi della traccia per identificare i concetti fondamentali e stabili del nostro dominio.

L'azienda "MareESole” noleggia barche a vela... di varie **marche**... Il **noleggio** riguarda il mezzo con una serie di possibili **extra**... è dato a un **cliente**... da una certa **data-ora** a una **data-ora**... in un certo **luogo**.

Ragionamento

Identifichiamo i concetti che rappresentano "valori" o categorie fisse. Per questi, usiamo `enum` per la type safety e classi immutabili per la robustezza.

public enum MarcaBarca {
    X_YACHTS, BAVARIA, GRAND_SOLEIL, BENETEAU
}

public enum TipoExtra {
    PULIZIA_FINALE, SKIPPER, CUOCO
}

public enum StatoNoleggio {
    PRENOTATO, IN_CORSO, CONCLUSO, ANNULLATO
}
Cliente.java

// ADT immutabile per il cliente
public final class Cliente {
    private final String id;
    private final String nome;
    // ... costruttore e getters ...
}
PeriodoNoleggio.java

import java.time.LocalDateTime;
import java.time.temporal.ChronoUnit;

// ADT immutabile per l'intervallo di tempo, con logica di business incapsulata
public final class PeriodoNoleggio {
    private final LocalDateTime dataInizio;
    private final LocalDateTime dataFine;

    public PeriodoNoleggio(LocalDateTime dataInizio, LocalDateTime dataFine) {
        if (dataInizio == null || dataFine == null || dataInizio.isAfter(dataFine)) {
            throw new IllegalArgumentException("Periodo non valido.");
        }
        this.dataInizio = dataInizio;
        this.dataFine = dataFine;
    }
    
    public long getDurataInGiorni() {
        long minuti = ChronoUnit.MINUTES.between(dataInizio, dataFine);
        if (minuti == 0) return 0;
        return (minuti - 1) / 1440 + 1;
    }
    
    // ... getters ...
}

Step 2: L'ADT `Barca` con il Pattern Builder

La traccia descrive la barca con molti attributi, alcuni dei quali opzionali.

...varie **dimensioni**, con 1 o 2 **alberi**, di varie **marche** ed eventuali altre **caratteristiche** (condizionatore, televisione, tendalini, età della barca, modello).

Ragionamento

Un costruttore con molti parametri è illeggibile e prono a errori. Il **Pattern Builder** è la soluzione ideale per costruire oggetti complessi in modo leggibile e per facilitare l'immutabilità.

Barca.java

public final class Barca {
    // Campi obbligatori (final)
    private final String id;
    private final MarcaBarca marca;
    // ...
    // Campi opzionali (final)
    private final boolean haCondizionatore;
    // ...

    // Costruttore privato che accetta solo il builder
    private Barca(BarcaBuilder builder) {
        this.id = builder.id;
        this.marca = builder.marca;
        // ... assegna tutti i campi dal builder ...
    }

    // ... solo getters ...

    // --- CLASSE BUILDER INTERNA E STATICA ---
    public static class BarcaBuilder {
        // Campi obbligatori
        private final String id;
        private final MarcaBarca marca;
        // ...
        // Campi opzionali con valori di default
        private boolean haCondizionatore = false;
        // ...

        public BarcaBuilder(String id, MarcaBarca marca, ...) {
            // ... inizializza campi obbligatori ...
        }

        public BarcaBuilder withCondizionatore(boolean presente) {
            this.haCondizionatore = presente;
            return this; // Interfaccia fluente
        }
        
        // ... altri metodi with... per opzionali ...

        public Barca build() {
            return new Barca(this);
        }
    }
}

Step 3: Gerarchia degli `Extra`

Gli extra hanno logiche di costo diverse, il che suggerisce polimorfismo.

...ogni **extra** costa in più (alcuni in **percentuale**, altri in **valore assoluto**...).

Ragionamento

Questo è un caso da manuale per una gerarchia di tipi. Creiamo un'interfaccia `Extra` che definisce il contratto comune (`calcolaCosto`) e classi concrete per ogni tipo di extra. Questo rispetta il **Principio Open/Closed**.

Extra.java

public interface Extra {
    String getNome();
    double calcolaCosto(Noleggio noleggio);
}
Skipper.java

public final class Skipper implements Extra {
    private final double costoGiornaliero;
    // ... costruttore ...
    
    @Override
    public double calcolaCosto(Noleggio noleggio) {
        return noleggio.getPeriodo().getDurataInGiorni() * this.costoGiornaliero;
    }
    // ...
}
PuliziaFinale.java

public final class PuliziaFinale implements Extra {
    private final double costoFisso;
    // ... costruttore ...

    @Override
    public double calcolaCosto(Noleggio noleggio) {
        return this.costoFisso;
    }
    // ...
}

Step 4: Pattern Strategy per i Costi

La traccia evidenzia che tariffe, sconti e penalità sono logiche variabili e soggette a frequenti modifiche.

La **tariffa**... **sconti** di diverso tipo... **penalità**... il valore delle tariffe, degli sconti e delle penalità viene **modificato molto frequentemente**.

Ragionamento

Questo è lo scenario perfetto per il **Pattern Strategy**. Incapsuliamo ogni regola di calcolo in una classe separata, rendendo il sistema flessibile e estensibile.

RegolaDiCalcolo.java

public interface RegolaDiCalcolo {
    double applica(Noleggio noleggio);
}
CalcolatoreCosto.java

import java.util.List;

// La classe Context dello Strategy Pattern
public class CalcolatoreCosto {
    private final List regole;

    public CalcolatoreCosto(List regole) {
        this.regole = regole;
    }
    
    public double calcolaCostoFinale(Noleggio noleggio) {
        return regole.stream()
                     .mapToDouble(regola -> regola.applica(noleggio))
                     .sum();
    }
}

Step 5: Repository e Query Pattern

Il sistema deve gestire collezioni di oggetti (la flotta, i noleggi) e permettere ricerche complesse.

...la **flotta di barche disponibili**... `cercare disponibilità` di una barca con **date caratteristiche desiderate**...

Ragionamento

Usiamo classi **Repository** (`Flotta`, `BookingManager`) per gestire le collezioni. Per le ricerche complesse, applichiamo il **Query Object Pattern** basato su un'interfaccia funzionale (o Specification), che si combina perfettamente con il pattern **Composite** tramite `default methods`.

CriterioRicercaBarca.java

@FunctionalInterface
public interface CriterioRicercaBarca {
    boolean isSatisfiedBy(Barca barca);
    default CriterioRicercaBarca and(CriterioRicercaBarca other) { /* ... */ }
    default CriterioRicercaBarca or(CriterioRicercaBarca other) { /* ... */ }
}
Flotta.java

public class Flotta {
    private final Set barche = new HashSet<>();
    
    public void aggiungiBarca(Barca barca) { /* ... */ }
    
    public List find(CriterioRicercaBarca criterio) {
        return barche.stream()
                     .filter(criterio::isSatisfiedBy)
                     .collect(Collectors.toList());
    }
}

Step 6: Facade (API) e Main

Infine, assembliamo il sistema e forniamo un punto di accesso semplice per il client, come richiesto dalla traccia.

Si necessita di un'**API** che consenta di implementare queste **operazioni principali**... e un **Main** che funga da client...

Ragionamento

La classe `API` applica il **Facade Pattern**. Nasconde la complessità dell'interazione tra `Flotta`, `BookingManager`, `CalcolatoreCosto` e `Factory`. Il `Main` interagisce solo con l'API, dimostrando un design ben disaccoppiato.

public class Main {
    public static void main(String[] args) {
        API api = new API(); // Il client conosce solo l'API

        // Scenario 1: Ricerca
        CriterioRicercaBarca criterio = (b) -> b.getDimensioneMetri() >= 12;
        List barcheTrovate = api.cercaDisponibilita(criterio, ...);
        
        // Scenario 2: Prenotazione
        if (!barcheTrovate.isEmpty()) {
            try {
                Noleggio noleggio = api.prenota(barcheTrovate.get(0), ...);

            }
        }
    }
}
